# Security Audit — 3.13.9 (2026-10-03)

**Scope.** Everything that landed after the 3.13.8 tag (`bbaecc4`). It was first written up as
part of 3.13.8 — this finding as §F8 of the
[3.13.8 audit](2026-10-02-3.13.8-ct-ecdh-ecdsa-sign-audit.md), the re-checks as notes added to
its §F2, §F5, §F6 and §F7 — but 3.13.8 had already been tagged and released, and a released
version is never re-cut, so the work is 3.13.9 and is recorded here; the 3.13.8 audit is back to
its released text. The finding keeps the number it was first given, **F8**, so a reference to
"§F8" means one thing; §R1–§R4 are the re-checks. Changed code:

1. the toolchain pin 6.6.9 → 6.6.14 (the maintainer's call, 2026-10-02), with `lib/` re-vendored
   and `cyrius.lock` re-locked (§R1–§R3 repeat the 3.13.8 audit's evidence on the new codegen);
2. `src/sys_util.cyr` (new `agnosys_rooted_paths_untrusted()`), `src/tpm_core.cyr`,
   `src/secureboot_core.cyr`, `src/ima_core.cyr`, `src/dmverity.cyr`, `src/luks.cyr` (§F8);
3. `[lib.secureboot]`, which now carries `src/sys_util.cyr` and so is self-contained;
4. every test and fuzz harness that wrote a fixed name in the shared `/tmp` (now a private
   per-run directory, `tests/scratch.cyr`), and CI's security scan, which now fails on a fixed
   `"/tmp/..."` literal in the tests and fuzz harnesses and on a bare file `sys_*` call.

**Result: one finding, fixed in this release** — F8 (MEDIUM, Windows, found while bumping the
pin). The re-checks find 3.13.8's constant-time and correctness results unchanged under 6.6.14.
No other finding at or above LOW; INFO residuals in §R4.

## F8 — On Windows the trust cores probed rooted POSIX paths (MEDIUM, fixed)

*Found while moving the pin to 6.6.14 — a cyrius review of sigil named the TPM helpers; the same
class was then looked for in every trust core.*

**What.** On Windows a rooted path is DRIVE-RELATIVE: `"/dev/tpmrm0"` opens `C:\dev\tpmrm0`, and
any authenticated user may create folders at the root of the system drive. The class is the one
cyrius closed in its own stdlib as CVE-54 (`C:\etc\hosts`), CVE-57 (`C:\etc\resolv.conf`) and
CVE-65 (`C:\etc\ssl\cert.pem`). sigil's trust cores (internalized at 3.8.1) probed such paths on
every target:

| Site | Path | Through 3.13.8 on Windows |
|---|---|---|
| `tpm_detect` (and `tpm_available`, which `tpm_seal_data` / `tpm_unseal_data` gate on) | `/dev/tpmrm0`, `/dev/tpm0` | a planted file reported a TPM |
| `_sb_tool_in` (mokutil / modinfo / kmodsign / ls lookups) | `/usr/bin/`, `/usr/sbin/`, `/bin/`, `/sbin/` | a planted `C:\usr\bin\mokutil` resolved; spawning it was refused by the subprocess helpers |
| `ima_get_status` | `/sys/kernel/security/ima/...` | reported IMA active with the planted log's line count |
| `ima_read_measurements` | `.../ascii_runtime_measurements` | returned the planted log as the measurement list |
| `ima_write_policy` | `.../policy` | wrote the policy into the planted file |
| `dmverity_supported` | `/sys/module/dm_verity` | reported dm-verity supported |
| `luks_keyfile_path` / `luks_write_keyfile` | `/tmp/.agnos-luks-<pid>-<hex>` | staged the LUKS key in a planted `C:\tmp`, a directory the other user owns |
| `luks_close` | `/dev/mapper/<name>` | answered Ok "nothing to close" (unplanted) |
| `secureboot_detect_state`, `secureboot_list_efi_variables` | `/sys/firmware/efi/...` | not reached: the `file_exists` gate opens the path as a file, which fails on a directory there |
| the module-signing sign-file fallback | `/lib/modules/<rel>/...`, `/usr/src/linux/...` | probed whenever `agnosys_uname` answered; the spawn that followed was refused, so Err either way |

Every subprocess helper (`agnosys_run_capture_timeout`, `agnosys_run_checked_timeout`) already
refuses on Windows, so no planted executable could be run; `tpm_seal` staged its plaintext in the
caller's `output_dir` before that refusal.

**Severity: MEDIUM.** Local attacker on the same Windows machine, and only against a program that
calls these helpers on Windows — they serve Linux mechanisms that do not exist there. But they
are public, a consumer that calls `ima_read_measurements` or `tpm_available` there gets
attacker-chosen answers to trust questions instead of "unavailable", and `luks_write_keyfile`
handed the key to that user.

**Fix.** `agnosys_rooted_paths_untrusted()` (`src/sys_util.cyr`) is 1 on Windows; each site
above asks it first and fails closed (`tpm_detect` 0; the TPM operations, `ima_read_measurements`,
`ima_write_policy`, `secureboot_list_efi_variables`, the sign-file fallback, `luks_keyfile_path`
and `luks_close` Err `not_supported`; `_sb_tool_in` 0; `secureboot_detect_state`
Ok(SB_NOT_SUPPORTED); `ima_get_status` inactive; `dmverity_supported` 0). `tpm_seal` refuses
before the plaintext is staged. Nothing changes off Windows. `[lib.secureboot]` gains
`src/sys_util.cyr`, where the helper (and the already-called `agnosys_capture_n`) live — the
profile was not self-contained before.

**Evidence.** `tests/tcyr/rooted_paths.tcyr`: on Windows 22 rows, 26 with `SIGIL_PLANT_ROOT=1`,
which plants every path above at the root of the current drive (run from a `subst` drive mapped
onto a scratch directory under `C:\cyrius-tests`), asserts the plants exist and removes them.
With the helper made to answer 0 — every guard off — cass fails 3 of 22 rows unplanted
(`luks_keyfile_path`, `luks_close`, the helper) and 11 of 26 planted (also `tpm_detect`,
`tpm_available`, the mokutil lookup, the four IMA rows, `dmverity_supported`,
`luks_write_keyfile`); under wine, where a rooted path is the Linux host's, 4 of 22. With the
guards: cass 22 / 0 and 26 / 0, wine 22 / 0. The unplanted run only sees a regression in the helper
itself: with `tpm_detect`'s guard alone removed it stays 22 / 0 while the planted run goes 24 / 2.
So the planted pass is checked in — `scripts/cass-rooted-paths.sh` (per-run directory under
`C:\cyrius-tests`, a free `subst` drive unmapped in a `finally`, the plants checked gone) — and is
mandatory whenever one of the five modules changes (CLAUDE.md, state.md).

**Not covered.** Paths the caller passes in (`secureboot_read_efi_variable(path)`,
`tpm_seal`'s `output_dir`, trust-store and keyring paths) are the caller's to choose; on Windows a
rooted one is drive-relative too.

## R1 — The constant-time check on cycc 6.6.14 (no finding)

The procedure of the 3.13.8 audit's §F2 (each function of the engine, ECDH and the signing core
disassembled from a `CYRIUS_SYMS` build; conditional branches counted — x86_64 `jcc`, aarch64
`b.cond` / `cbz` / `cbnz` / `tbz` / `tbnz` — and each accounted for), on `ecdh.tcyr` and
`ecdsa_sign.tcyr` built with 6.6.14's `cycc` and `cycc_aarch64`, gives exactly the counts of that
table for every function in it and for the helpers not in it (`_ect_ctx_new` 3, `_ect_on_curve`,
`_ect_to_mont`, `_ect_from_mont`, `_ect_inv` 0), on both architectures — and the 6.6.9 builds,
counted by the same script, reproduce the table, so the script and the table agree. The core
functions (`_ect_mul`, `_ect_padd`, `_ect_pdbl`, `_ect_lookup`, `_ect_smul`, `_ect_pow`,
`_ect_add`, `_ect_sub`, `_ect_reduce_be`, `_nmul64_hi_sw`, `_ecdh_shared`, `_ecs_sign_core`)
compile to the same instruction sequence under both toolchains, addresses aside.

## R4 — Residuals (INFO)

- **Codegen dependence.** The constant-time contract holds for the code cyrius 6.6.9 and 6.6.14
  emit (3.13.8 audit §F2, §R1 here). A future compiler that turned a mask expression into a branch
  would break it; the disassembly check in architecture note 004 is how to re-verify after the
  next toolchain bump.
- **Paths a caller passes in** — F8 "Not covered".
- Everything else in the 3.13.8 audit's §F7 stands unchanged.
