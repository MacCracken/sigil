# Security Audit — 3.13.6 (2026-10-01)

**Scope.** The three sigil-side defects behind cyrius's 2026-09-30 TLS issues
(`tls-first-use-thread-race`, and part (e) of `tls-client-memory-and-alert-gaps`):

1. ~30 lazily-built tables guarded by plain check-then-set flags (first use from two threads
   corrupted them, permanently);
2. `crypto_tls_main_init` installing a thread-local block on whichever thread arrived first
   (a worker-first process killed its main thread: SIGSEGV);
3. `x509_parse` refusing any certificate whose own signature algorithm it could not verify
   (8 of 121 roots in a stock trust store never installed).

**Result: no findings at or above LOW in the changed code. Three residuals are named in the
roadmap for the maintainer's decision (§R).** This is the first audit filed since 3.12.9; 3.13.0
through 3.13.5 filed none (see state.md's audit row).

## F1 — SHA-1 RSA certificates: parsed, never verified (INFO, deliberate posture)

`_xp_parse_sig_algid` now recognises `sha1WithRSAEncryption` (1.2.840.113549.1.1.5) as
`X509_SIG_RSA_SHA1`, with the same RFC 4055 explicit-NULL parameters rule as the other RSA
OIDs and the same inner/outer AlgorithmIdentifier equality check (RFC 5280 §4.1.1.2 — the
algorithm-substitution guard is unchanged).

Checked:

- **No path verifies a SHA-1 signature.** `_x509_verify_link` returns 0 for `X509_SIG_RSA_SHA1`
  explicitly (not only by falling through), and there is no SHA-1 PKCS#1 verify in `rsa.cyr` to
  reach. `x509_rsa.tcyr` proves it with a GENUINE SHA-1 link signature (openssl verifies it):
  `_x509_verify_link` and `x509_verify_chain` both return 0. SHA-1 has practical chosen-prefix
  collisions (2020), which is exactly why only verification matters here.
- **Where a SHA-1 certificate can now succeed, its own signature was never what was checked.**
  - `x509_verify_chain` never verifies the ROOT's signature — an anchor is trusted as given
    (RFC 5280 §6.1) — so a root self-signed with SHA-1 now anchors a chain whose links are
    SHA-256/384/512.
  - cyrius's `tls_native` anchors with `_x509_issuer_matches` + `_x509_verify_link(cur, root)`:
    same property.
  - SGX / TDX / SEV-SNP anchor at a caller-supplied root through `x509_verify_chain`; a SHA-1
    link in a quote chain is still refused.
  - Authenticode **mode 0** trusts a signer certificate by byte-equality with the pinned
    `db` certificate; a SHA-1-signed pinned certificate now parses there, and the PE's own
    CMS signature is still verified with its key. That matches firmware, which treats a `db`
    certificate as an anchor. **Mode 1** goes through `x509_verify_chain` (SHA-1 links refused).
- md5WithRSA and every other unknown OID still fail `x509_parse`.

## F2 — SHA-512 RSA link verification (INFO)

`_rsa_pkcs1v15_verify_sha512` (private) mirrors the SHA-256/384 verifiers: SHA-512 over the TBS
into a 64-byte per-call buffer, the RFC 8017 §9.2 note 1 DigestInfo prefix
`30 51 30 0d 06 09 60 86 48 01 65 03 04 02 03 05 00 04 40` (checked byte by byte against the
RFC), then the shared `_rsa_pkcs1v15_check` — RSAVP1 with the s < n and odd-n checks and the
OR-accumulating constant-time EM compare. No new comparison code. Tests: a genuine SHA-512 link
verifies; a tampered one and the same signature under another RSA key are refused; and the real
D-TRUST BR Root CA 2 2023 parses.

## F3 — Lazy-init claim / publish (INFO)

31 flag inits now use `_sigil_once_claim` (CAS 0 → 1; losers spin until 2, then fence) /
`_sigil_once_publish` (fence, store 2), with an acquire fence on the aarch64 fast path. 15
pointer-checked scratch allocations CAS-publish their pointer (`_sigil_lazy_scratch`).

Checked:

- **Ordering.** x86 is TSO; on aarch64 the publish is `dmb ish` + store and both read paths
  fence after observing 2. Scratch blocks need no ordering for their CONTENTS (written before
  read on every use); the pointer itself is published by an acquire-release CAS.
- **No build returns between claim and publish.** Verified mechanically for all 31 (exactly one
  `return` per build, after the publish) — an early return would leave the flag at 1 and spin
  every later caller forever.
- **No deadlock.** A build that reached its own init would have recursed without bound under the
  old code, so none does; nested claims (`_ecv_init` → `_build_p256_G_table` → `_p256_init`) form
  no cycle.
- **`p256/p384_scalarmul_base`** no longer test the table flag against 0 themselves (under 0/1/2
  that would read a half-built table); they call the builder, whose fast path is one load.
- **Leak bound.** A losing `_sigil_lazy_scratch` caller abandons its block (no free on the bump
  heap): at most one block per pointer per losing thread, once — under 40 KB per losing thread
  across the 15 pointers.
- **Regression gate.** CI's security scan fails on either check-then-set shape (31 + 15 hits on
  3.13.5, 0 now).
- `lazy_init_race.tcyr`: 6 of 6 cold trials gave wrong answers on 3.13.5 (no false accepts were
  observed — the reject arms held); 0 of 6 now, stable.

## F4 — `crypto_tls_main_init`: only a thread without a block gets one (INFO)

On Linux the calling thread's thread pointer decides (`_crypto_needs_block`): > 0 = it has a
block (every `thread_create` worker; or a main thread the program equipped) and is left alone;
0 = none (only ever the main thread) and installs one, taking bank 0.

Checked:

- **`rdfsbase` is never executed unless the kernel enabled it.** `_sigil_fsgsbase` reads
  `/proc/self/auxv` (512-byte per-call stack buffer, at most 512 bytes read, a loop bounded by
  `i + 16 <= n`, stops at AT_NULL) and only bit 1 of AT_HWCAP2 (HWCAP2_FSGSBASE) enables it;
  any failure means "unavailable" and the tid == pid fallback (correct, slower). The open is
  Linux-only; agnos, macOS and Windows never compile the read (the target macros are mutually
  exclusive in cycc).
- **The hand-encoded reads are pinned.** `rdfsbase rax` / `mrs x0, TPIDR_EL0` store into the
  first local's frame slot; `cbank_main_lane.tcyr` group 3 checks that the value is 0 on a cold
  main thread, then exactly the block holding main's slots, and a worker's own block — on
  x86_64, aarch64 under qemu and on real aarch64.
- **A worker never takes bank 0 or replaces its block** (the old behaviour wiped every other
  library's slots on that worker). A main thread that already had a block draws a pool lane
  instead of bank 0 — one lane of the 63 — rather than having its block replaced.
- **Fallback cost**, not a correctness gap: on x86 without FSGSBASE every `cbank()` before the
  main thread's block exists makes two syscalls (~660 ns measured here).

## F5 — Dead code (INFO)

`x509.cyr`'s `_xp_buf` / `_xp_buf_len` / `_xp_cert` / `_xp_cp` / `_xp_np` / `_xp_n2p` /
`_xp_alloced` and `_xp_init` were referenced nowhere but their own initialiser (24 bytes
allocated per process, never read). Removed rather than converted.

## R — Residuals, named in the roadmap for the maintainer

- **ECDSA P-521** — the one stock-store root still refused (e-Szigno TLS Root CA 2023). A new
  curve is a feature.
- **x86 kernels without FSGSBASE (before Linux 5.9)** — the main thread still installs a fresh
  block over one the program installed itself, as before 3.13.6.
- **`fork()` during a first-use build** — a child forked while another thread holds a claim
  spins forever on that table if it uses it without exec. Inherent to claim/publish; the five
  3.13.1 inits already had it.

## Verification

Suite 82/82 files; the three changed test files pass on x86_64, aarch64 (qemu and the pi), ecb
(macOS arm64) and ach (macOS x86_64; the race test skips there — serial threads). Threading
tests were red on 3.13.5 (6/6 trials wrong; worker-then-main killed by signal 11; main's own
slot wiped) and the X.509 additions failed 18 of 18.
