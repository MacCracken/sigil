# Security Audit — 3.12.2 native asm multiply, public-exponent modexp, Authenticode verify

**Date:** 2026-07-30
**Scope:** The three new/changed surfaces of 3.12.2, plus the toolchain bump
(`6.4.65` → `6.5.3`) and dependency bump (sakshi `2.4.3` → `2.4.7`,
bayan `1.1.0` → `1.3.0`):

1. **`src/mul64.cyr`** — a new hand-written `asm{}` block on the hottest path
   in the library, consumed by `src/bignum.cyr`, `src/bigint_ext.cyr` and
   `src/ecdsa_p384.cyr`. Only the third `asm{}` site in `src/`, and the first
   with no runtime feature dispatch.
2. **`src/bignum.cyr` `bn_mont_modexp_pub`** — a *deliberately* non-constant-time
   modexp, which must be proven unreachable from any secret exponent.
3. **`src/authenticode.cyr` `authenticode_pe_verify` + the P-256 signer** — a
   brand-new parser for wholly attacker-controlled input (PE image + PKCS#7 +
   X.509), the class in which this module already shipped a 1–2 byte OOB read
   at 3.10.1.

**Result:** **1 HIGH fixed** (a correctness/availability defect in *shipped*
signing code, found during this audit's spec review, not by a test), **4
defense-in-depth hardenings applied**, **1 LOW fixed**, **2 INFO recorded**.
No CRITICAL. Suite **1661/0 across 64 files**; fuzz **24/0** across 3 files.

---

## Findings

### F1 — HIGH — `authenticode_pe_sign` signed a byte range no verifier checks

**File:** `src/authenticode.cyr`, `authenticode_pe_sign` (shipped 3.10.0).

The signer computed the Authenticode digest over `pe[0, pe_len)`, then wrote
the attribute-certificate table at `cert_start = (pe_len + 7) & ~7`,
zero-filling `[pe_len, cert_start)`. The Authenticode specification hashes the
image **up to the start of the certificate table**, which includes that pad.
For any `pe_len` not a multiple of 8 the signature therefore covered a
different byte range than firmware, `sbverify` and Windows recompute.

**Why it survived three releases.** PE file alignment is 512 and the only test
fixture is 256 bytes — both 8-aligned, where the two spans coincide exactly.
The openssl validation recorded in the driving issue (`dgst -sha256 -verify` →
`Verified OK`) does **not** cover it either: that verifies the RSA signature
over the SpcIndirectData DER, not that the embedded PE hash equals what a spec
verifier recomputes.

**Severity: HIGH, but read the direction.** This is **not** a forgery or
key-recovery defect and does not let anything wrong be *accepted* — a mismatched
image hash fails closed everywhere. It is a correctness/availability defect on
the sovereign UEFI Secure Boot path: sigil would emit a structurally valid
signature on an image that firmware **rejects**, i.e. an unbootable system. It
is rated HIGH rather than MEDIUM because the failure lands on the boot chain,
the artifact is long-lived, and the defect is silent at signing time.

**Fix.** The image and pad are laid down first; the digest is taken over
`out[0, cert_start)`. Aligned inputs — everything gnoboot signs today —
produce **byte-identical** signatures to 3.12.1.

**Regression test, mutation-proven.** `tests/tcyr/authenticode.tcyr` signs a
deliberately unaligned **253-byte** image and verifies it. Reverting only the
signer's hash range to the 3.12.1 body makes exactly that one assertion fail
while every aligned case still passes — confirming both that the test catches
the bug and that the old suite could not have.

### F2 — LOW — 144-byte leak per `authenticode_pe_hash`, on a non-thread-safe allocator

`authenticode_pe_hash` obtained its SHA-256 context from `sha256_init()`, which
is `fl_alloc(144)` and whose contract (`src/sha256.cyr`) requires the caller to
`fl_free` after `sha256_finalize`. It never did. Two consequences: a 144-byte
freelist leak on every call, and a dependency on `fl_alloc`, which mutates
shared state and is unsafe under concurrent fan-out (quirk #7).

Not exploitable on the current one-shot signing path, hence LOW — but the
verify path added in this release calls the same core, and a verifier is
exactly the thing a consumer runs in a loop on hostile input.

**Fix.** The context is now a `cbank()`-banked lane plus `sha256_init_into`:
allocator-free and race-free. The same pattern is used for the signedAttrs
re-tag digest in `_ac_verify_sig`.

### F3 — Hardening (×4) — PE header fields accepted without validation

Found by enumerating every attacker-controlled field the walk depends on.
None is known-exploitable in the 3.12.1 code — all reads stayed in-file, so
these are semantic rather than memory-safety defects — but each let a crafted
image steer the parse:

| Field | Before | Now |
|---|---|---|
| Optional-header magic | only `0x10B` tested; **anything else treated as PE32+** | allow-list `{0x10B, 0x20B}`, else reject |
| `NumberOfRvaAndSizes` | never read | must be `>= 5`, else there is no entry 4 to read and section-header bytes would be parsed as a security directory |
| `e_lfanew` | upper-bounded only | must also be `>= 0x40`, so the PE header cannot claim to start inside the DOS stub |
| Certificate table | not validated | 8-byte aligned, `>= secdir + 8` (disjoint from the hashed headers), inside the file, and `tab_off + tab_size == pe_len` (the trailer) |

The trailer requirement is the load-bearing one: without it, a region exists
that is neither hashed nor signed yet sits inside a file that verifies —
attacker-appendable content in a "valid" image.

### F4 — INFO — the asm multiply IMPROVES the constant-time posture

Recorded because the intuition runs the other way. `_nmul64` / `_nmul64_hi`
replace a portable 32-bit-halves decomposition that carries **two
value-dependent branches per product** (the `mid_carry` / `lo_carry` fixups).
`MUL r/m64` is data-independent on every x86-64 microarchitecture sigil
targets. On RSA's secret-exponent ladder and ECDSA P-384's signing nonce, this
removes two data-dependent branches per limb product. There is no side-channel
cost to weigh against the speed-up. The aarch64 fallback keeps the old shape,
so that target is unchanged, not worsened.

### F5 — INFO — `bn_mont_modexp_pub` is non-constant-time **by design**; reachability proven

The new modexp branches on exponent bits. That is correct only if no secret
exponent reaches it. Verified by exhaustive call-site review:

| Call site | Exponent | Schedule |
|---|---|---|
| `src/rsa.cyr:133` `_rsa_recover_em` | `e_be` from `rsa_pubkey_from_der` | `_pub` — public key material |
| `src/rsa.cyr:593` sign path, blinding `r^e` | `key + RSAK_E` | `_pub` — `e` is public; the *base* `r` is secret but never steers control flow |
| `src/rsa.cyr:610` sign path, verify-after-sign `s^e` | `key + RSAK_E` | `_pub` — public |
| `src/rsa.cyr:488` `_rsa_crt_modexp`, `dp` | **secret** | **unchanged — `bn_mont_modexp`** |
| `src/rsa.cyr:489` `_rsa_crt_modexp`, `dq` | **secret** | **unchanged — `bn_mont_modexp`** |
| `src/rsa.cyr:600` full-width fallback, `d` | **secret** | **unchanged — `bn_mont_modexp`** |

`grep -n 'bn_mont_modexp\(_pub\)\?(' src/*.cyr` confirms these are **all six**
call sites in the tree — three converted, three secret-exponent ones untouched
— and that no module other than `rsa.cyr` calls either entry point.

The blinding case deserves the explicit note above: the *base* is the secret
blinding factor `r`, but the schedule depends only on the exponent, so
switching schedules leaks nothing about `r` that the ladder did not.

Policy recorded in [ADR 0008](../adr/0008-native-asm-multiply-and-public-modexp.md).

## Posture review

- **Input validation.** Every structural read on the verify path goes through
  either the explicit bounds checks in `_ac_pe_dirs` / `_ac_cert_table` /
  `_ac_win_cert` or through x509.cyr's audited `der_walk`, which enforces
  `pos < buf_len`, rejects indefinite lengths, rejects length fields wider
  than 4 bytes, and rejects any TLV whose content would run past the buffer.
  There is no raw pointer arithmetic on untrusted offsets outside those three
  helpers. Every DER cursor loop carries an iteration guard **and** a
  strictly-advancing check (`next > cur`), so a zero-length element cannot
  spin. Structural slack is rejected rather than ignored: `[0]` wrappers,
  SignerInfo, and the SpcIndirectData `messageDigest` must each end exactly
  where their parent does, and the `SET OF` in a signed attribute must hold
  exactly one value filling it.
- **Integer overflow.** `tab_off` and `tab_size` come from `_pe_rd32`, so each
  is in `0..2^32-1` and the i64 sum cannot wrap — the reason the table checks
  can be plain comparisons. A near-`2^32` offset is covered by a negative test.
- **Buffer safety.** The new `var` arrays were each checked for BYTE sizing
  (quirk #3): `var ctx[9216]` = 144 × 64 banks, `var desc[7168]` = 112 × 64,
  `var raw_dsig[4096]` = 64 × 64. Max access offset is below N in each case.
- **Constant-time.** The image-hash compare, the signedAttrs `messageDigest`
  compare, and the trust-anchor DER compare all use `ct_eq_bytes`
  (OR-accumulating), and the anchor compare is length-checked *before* the
  byte compare so it cannot read past either operand. This is
  belt-and-braces — every operand on the verify path is public.
- **Key zeroization.** No new secret buffer. `_bn_mont_scrub_lanes()` still
  runs on `bn_mont_modexp_pub`'s return even though its operands are public,
  keeping one hygiene surface: a public call landing on a lane a prior secret
  call used still leaves it clean. `_ecdsa_p256_verify_digest_der` wipes its
  banked `r‖s` lane on every path including the error paths.
- **Thread-safety.** The banked scratch follows quirk #1 / #9 — plain `var` +
  per-lane `memset`, never `secret var`. `grep 'secret var [a-z_]*\['` over the
  changed modules returns nothing new. **Stated honestly:**
  `authenticode_pe_verify` is **single-threaded by construction** — it calls
  `x509_parse` / `x509_verify_chain`, which are, and it owns a module-level
  arena reset per call. Its banked SHA-256 contexts and descriptor are banked
  because banking is free, *not* because the entry is re-entrant. That
  contract is written into the module header.
- **Allocation.** The verify path takes its cert structs and RSA key blocks
  from a module-owned arena that is `arena_reset` at the top of every call, so
  repeated verification does not drift the global bump heap (the 3.7.3 `_into`
  motivation). It never calls `alloc` / `vec_*` / `fl_alloc` on untrusted
  sizes; `AC_MAX_P7` (32 KB), `AC_MAX_SIGNED_ATTRS` (8 KB) and
  `AC_MAX_EMBEDDED_CERTS` (8) bound the parse work.
- **Syscalls / command execution / path traversal.** None added. No
  `sys_system`, no `exec_*`, no filesystem path from external input.
- **Dependency review.** bayan `1.3.0` ships a breaking rename
  (`bayan_json_v_parse_str` → `_parse_buf`) motivated by a cyrius
  overload-dispatch defect. **sigil is unaffected** — grep confirms it uses
  only the `u256_*` compat aliases and `_mul64`, none of which carry a
  reserved `_str`/`_int`/`_cstr` suffix. sakshi `2.4.7`'s equivalent rename
  is internal and `_`-private.
- **Known-CVE classes re-checked** for this surface: Authenticode
  attribute-certificate-table confusion (addressed by the trailer requirement
  and the single-entry rule), CMS `signedAttrs` substitution (addressed by
  verifying `contentType` **and** `messageDigest` against the actual content),
  PKCS#1 v1.5 signature-forgery via unchecked padding (unchanged — the
  rebuild-and-compare `_rsa_pkcs1v15_check` verifies all `k` octets), and
  DER length-field overflow (delegated to the audited `der_walk`).

## Verification

- Full suite **1661 / 0 failed** across 64 `tests/tcyr/` files (1587 before);
  `bignum.tcyr` 14 → 33, `authenticode.tcyr` 5 → 60.
- Fuzz **24 / 0** across `fuzz/fuzz_ed25519` (11), `fuzz_integrity` (6),
  `fuzz_revocation` (7).
- Concurrency race-detectors green: `banking_concurrent`,
  `concurrent_tls_handshake`, `bignum_tls12_concurrent`, `ecdsa_concurrent`.
- The multiply is differentially KAT'd against bayan's `_mul64` on 17
  adversarial operand pairs in both argument orders, plus the `(2^64-1)²`
  maximum, a pure-low product (proving `*out_hi` is written, not left stale),
  an aliased-output case pinning the store order, and an equivalence check of
  the aarch64 fallback against the asm path.
- F1's regression test is **mutation-proven** (see F1).
- **The CMS `signedAttrs` path is validated against an INDEPENDENT
  implementation, not a self-round-trip.** sigil's own signer never emits
  signedAttrs, so a sign→verify test would have left the whole third-party
  branch — the `0xA0` → `0x31` re-tag, the `contentType` / `messageDigest`
  attribute binding, and `sha256WithRSAEncryption` — completely unexercised.
  `tests/tcyr/authenticode.tcyr` therefore carries a signed image built by a
  separate Python DER writer + `cryptography` RSA signer over the same
  synthetic PE, with the third-party shape throughout. It verifies, and its
  tampered-body and tampered-signature mutations fail at the expected steps
  (`AC_VERR_IMAGE_HASH` / `AC_VERR_SIGNATURE`) rather than merely failing.
- The toolchain bump was verified in isolation first: **1587 / 0 at 6.5.3 with
  no source change**, identical to 6.4.65, so no 3.12.2 result is
  attributable to the compiler.
