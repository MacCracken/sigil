# Security Audit — 3.13.7 (2026-10-02)

**Scope.** One sigil-side defect recorded by the cyrius 6.6.13 I2 review:
`pem_decode_certs_into` is all-or-nothing, so one malformed block (an unmatched BEGIN, bad
base64) failed a whole trust bundle, and cyrius's native TLS installed **zero** roots from an OS
store with one corrupt block. Changed code, all in `src/pem.cyr`:

1. `pem_decode_certs_lenient_into` (new, public) — skips a malformed block, decodes every other
   one, counts what it skipped;
2. `pem_count_cert_blocks` (new, public) — the block count that walk visits;
3. `_pem_b64_decode` is now a wrapper over `_pem_b64_walk`, which adds a validate-only (`dry`)
   mode and reports a full output buffer (-2) apart from a malformed body (-1).

**Result: no findings at or above LOW.** One INFO observation about the unchanged strict decode
(§F4), recorded and deliberately not changed.

## F1 — Lenient decode: memory safety (INFO)

The input is treated as fully attacker-controlled, as for the strict decode (a trust bundle is
normally a root-owned file, but the function cannot know who wrote its bytes).

Checked:

- **Reads.** Every read goes through `_pem_find` / `_pem_match_at` (bounded by `pem_len`:
  `pos + len > buf_len` returns 0 before any byte is read) or `_pem_b64_walk` over
  `[body_start, end_off)`, where `end_off` is a match position `<= pem_len - 25`. A block with
  no END is never walked. Resuming at `body_start` (after a failure) or at `end_off` (after a
  success) is always `<= pem_len`; `_pem_find` from there returns -1 when no marker fits.
- **Writes.** `out_chain` entries are written only for a decoded block and only after
  `count < max_certs` is checked, at `count * 16` — so `max_certs * 16` bytes bound them, and
  entries past the returned count are untouched (tested with a sentinel). Pool writes happen only
  in `_pem_b64_walk` with `dry == 0`, after `op + out_n > out_max` is checked, with
  `out_max = der_pool_size - pool_used`; `pool_used` grows only by a successful decode's length,
  which is `<=` that bound, so it never exceeds `der_pool_size`. `dry == 1` writes nothing — the
  validate-only walk is called with `out = 0` and `out_max = 0`; a mutant that took the writing
  path in dry mode was caught (its dry walk answers -2, so a well-formed block after a full pool
  is skipped instead of failing, and three assertions go red).
- **Null and negative arguments.** `pem_len < 0`, `max_certs <= 0`, `der_pool_size < 0`, a null
  `out_chain`, and a null `pem` / `der_pool` with a non-zero length all return -1 before any
  access. `out_skipped` may be 0 (not written).
- **A malformed block consumes nothing.** A partial decode writes into the pool before its defect
  shows; `pool_used` is not advanced, so the next block overwrites it. Tested with a
  certificate-sized block whose only defect is its last body byte, between two good blocks, in a
  pool exactly the size of the two good DERs.

## F2 — Lenient decode: what it accepts (INFO)

Lenience must remove roots, never add or alter one.

- **Every decoded entry is exactly what the strict decode produces for that block alone**: the
  same `[BEGIN + 27, END)` body through the same base64 walk. No entry is assembled across block
  boundaries — where the strict decode, given an unmatched BEGIN, walks from that BEGIN to the
  NEXT block's END (and fails on the `-` of the BEGIN text inside), the lenient decode skips the
  unmatched block and resumes at the next BEGIN, never after the END it ran into. A mutant that
  resumed after that END lost the following certificate and was caught.
- **A skipped block is a missing root, never an extra one.** Certificate validation is unchanged
  downstream (`x509_parse` + chain verification); a server chaining to a skipped root fails
  verification, which is fail-closed, and the skipped count makes that visible to the caller.
- **Capacity is not malformation.** A WELL-FORMED block that finds no entry or no pool space
  returns -1 (with `out_skipped` 0), so an undersized buffer is never mistaken for a bad bundle
  or reported as "skipped". When the pool runs out mid-walk (-2), a validate-only walk decides:
  a malformed block is skipped whatever the pool's size, a well-formed one is the failure. Both
  directions are mutation-tested.
- **The count invariant.** For every non-negative return, `decoded + skipped ==
  pem_count_cert_blocks(pem, pem_len)`: both enumerate BEGIN markers left to right, each search
  starting 27 bytes after the previous match. After a decoded block the walk searches from its
  END rather than its body start; that is the same marker, because a body that decodes is
  base64 and whitespace only and cannot contain the `-` a BEGIN starts with. The same rule as
  cyrius's own `_tn_pem_block_count`, so cyrius's `blocks − stored` keeps meaning what it says.
  Checked over 400 generated bundles against a model.

## F3 — Complexity (INFO)

A bundle is walked in linear time. The first END after a body start is cached and reused while it
still lies past the current body start, so a run of unmatched BEGINs followed by one distant END
(or by none, cached as -1) does not rescan the tail once per block; each next-BEGIN search starts
after the previous match. A malformed body stops the base64 walk at its first bad byte. Measured
on the 121-block Arch store: 2.71 ms lenient vs 2.68 ms strict per decode; the strict decode is
2.66 ms on both 3.13.6 and 3.13.7 (the `dry` branch costs nothing measurable).

## F4 — The strict decode's blind spot is unchanged (INFO, no action)

An END marker whose trailing five dashes double as the next BEGIN's leading five
(`-----END CERTIFICATE-----BEGIN CERTIFICATE-----`) is not RFC 7468 PEM. The strict decode
resumes 25 bytes after the END, past that BEGIN, and silently returns one certificate fewer;
the lenient decode and `pem_count_cert_blocks` both find it. The strict behaviour is kept on
purpose: it is the decode for attestation chains, where a missing certificate fails chain
verification (fail-closed), and this release does not change what it returns for any input.
`pem.tcyr` pins both behaviours.

## Tests

`tests/tcyr/pem.tcyr` 39 → 158 assertions: one bad block first / middle / last (plus a
certificate-sized one whose defect is its last byte), unmatched BEGIN first / middle / last and a
run of three at the tail, every malformed-body kind (empty, excess padding, alphabet after
padding, partial quad, bad byte) with a stray END, all bad, no BEGIN, empty input, `out_chain`
and `der_pool` capacity edges in both directions, every bad argument (and each check again on
an input where nothing else returns -1), survivors parsed and chain-verified, the END/BEGIN dash
overlap, two overlapping BEGIN markers (one block, skipped: the walk and the count agree), and
400 generated bundles against a model (decoded entries, skipped count, block count, and the
strict decode's answer unchanged).

On 3.13.6 the file does not compile (the two functions are undefined). 17 mutants of the new code
— all-or-nothing on a bad block, resuming after the END on failure, an entry claimed before the
block decodes, a full pool always skipped / always fatal, an unmatched BEGIN at the tail not
counted, the END searched only once, the count stepping too far, the dry walk writing, a success
resuming past its END, a skipped block consuming pool, an off-by-one entry check, an empty
input counted as -1, the count stepping one byte past a match instead of 27, a skip resuming at
the BEGIN + 1, and the `max_certs <= 0` / `der_pool_size < 0` checks removed — each fail it. The
last four passed the first cut of the file (review found them); the overlapping-BEGIN group and
the decide-alone argument checks pin them. Passing on x86_64 Linux, the pi (aarch64), ecb (arm64
macOS), ach (x86_64 macOS) and cass (Windows PE), toolchain 6.6.9.
