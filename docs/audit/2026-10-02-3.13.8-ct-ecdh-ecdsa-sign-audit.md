# Security Audit — 3.13.8 (2026-10-02)

> Post-release: see the [3.13.9 audit](2026-10-03-3.13.9-pin-bump-windows-rooted-paths-audit.md) (the pin bump to 6.6.14 and §F8, the trust cores' rooted POSIX paths on Windows).

**Scope.** cyrius's native TLS 1.2 client needs ECDHE on P-256 / P-384 (cyrius 6.6.14 lists a
P-256 / P-384 client certificate's curve in `supported_groups`; a server preferring it, or an
OpenSSL server with an ECDSA P-256 / P-384 certificate, fails the handshake today). That needs a
scalar multiplication constant-time in the private key, which sigil did not have. The premise
check asked whether the existing ECDSA signing ladder could serve, and found that it ran its own
secret on variable-time arithmetic (§F1). Changed or new code:

1. `src/ec_ct.cyr` (new) — the constant-time engine; `pt_scalarmul_secret` /
   `pt384_scalarmul_secret` moved here;
2. `src/ecdh.cyr` (new) — `ecdh_p{256,384}_keygen`, `ecdh_p{256,384}_shared`;
3. `src/ecdsa_sign.cyr` — signing core on the engine; RFC 6979 candidate test branch-free;
4. `src/mul64.cyr` — `_nmul64_hi_sw` branch-free;
5. `src/ecdsa_p256.cyr`, `src/ecdsa_p384.cyr` — the k_hat / blinding helpers removed, comments
   corrected (nothing there is constant-time);
6. `scripts/check.sh` — private temporary directory;
7. after review of the first draft: `src/hmac.cyr`, `src/hmac_sha384.cyr`, `src/sha384.cyr`
   (context / inner-hash / finalize-scratch wipes), `src/sha_ni.cyr`, `src/aes_ni.cyr` (register
   scrubs), `src/crypto_scratch.cyr` (`_sigil_wipe64`), the signers split into a burning wrapper
   and a secret callee, and `tests/tcyr/batch_parallel.tcyr` / `tests/bcyr/batch_parallel.bcyr`
   (per-run temporary files).

**Result: two findings, both fixed in this release** — F1 (HIGH, the premise check) and F4
(MEDIUM, found by the review of the first 3.13.8 draft, which had recorded F4 as "no finding").
No other finding at or above LOW in the new code; INFO residuals in §F7.

## F1 — ECDSA signing ran the secret nonce and key through variable-time arithmetic (HIGH, fixed)

**Where (3.13.7).** `ecdsa_p256_sign` / `ecdsa_p384_sign` → `pt_scalarmul_secret` →
`_pt_ladder` → `pt_add` / `pt_double` → `fp_p256_*` → `u256_mul_full` + `_p256_solinas_reduce`
(P-384: the `u384_*` / `fp_p384_*` twins), then `pt_to_affine` (`fp_p256_inv` on Z), then
`fn_p256_inv(k)` and `fn_p256_mul(r, d)` / `fn_p256_mul(k^-1, e + r·d)` (`n_reduce`, a bit-serial
long division), and `_ecs_addmod_n_p256`.

**Data-dependent branches reached with secret-derived operands** (every one confirmed in source):

| Site | Branch |
|---|---|
| `fp_p256_add` | `if (carry == 1)`, `if (u256_cmp(r, p) >= 0)` |
| `fp_p256_sub` | `if (borrow > 0)` |
| `_p256_sol_red1` (×9 per reduction) | `if (u256_cmp(t, p) >= 0)` |
| `u256_cmp` / `u256_is_zero` (bayan) | early exit at the first differing / non-zero limb |
| `u256_mul_full` (Karatsuba) | seven `if ((x ^ sbit) < (y ^ sbit))` carry fix-ups, `if (cs == 1)` / `if (ct == 1)` corrections |
| `_u256k_mul128` | two carry `if`s per product |
| `_nmul64_hi_sw` (aarch64: pi, ecb) | two carry `if`s per 64×64 product |
| `fp_p384_add` / `fp_p384_sub`, `u384_add` / `u384_sub` / `u384_cmp` / `u384_is_zero` / `u384_mul_full`, `_p384_sol_red1` | the same shapes at six limbs |
| `n_reduce` / `n384_reduce` | per-bit `if (carry == 1) ... else if (cmp >= 0)` over the product of k^-1 or r with d |
| `_ecs_addmod_n_p256/p384` | `if (carry == 1)` / `if (cmp >= 0)` on e + r·d |
| `pt_add` / `pt_double` | early return on an infinity operand (first ladder step only, after 3.13.0), `H == 0` special cases |
| `_rfc6979_k_p256/p384` | `u*_is_zero` / `u*_cmp` early exits on the accepted candidate k |

The 3.13.0 k_hat fixed the coarse leak (ladder length tracked bitlen(k)) and 3.13.1's blinding the
Z = 1 operand of the second step; neither touched the arithmetic. The 3.7.0 and 3.7.17 audits
recorded the field arithmetic as a known INFO residual "mitigated by RFC 6979 deterministic
nonces + AGNOS's single-tenant deployment". RFC 6979 does not help against timing (each message
gives a different k), and since cyrius's native TLS signs CertificateVerify with these functions
— a server signs once per handshake, for anyone who connects — the deployment argument no longer
holds.

**Measured.** A fixed-vs-random Welch t-test (dudect method; 10% upper crop per class) on
`pt_scalarmul_secret`, k = 1 against uniformly random 255-bit k, classes interleaved at random,
x86_64 dev host:

| Build | samples | mean k = 1 | mean random | Welch t |
|---|---|---|---|---|
| 3.13.7 | 400 | 9045.7 µs | 9085.3 µs | **-6.34** |
| 3.13.8 | 1200 | 2826.3 µs | 2827.4 µs | -0.69 |

|t| > 4.5 is dudect's "leak detected" threshold. The 3.13.7 difference is 0.4% per call — small,
data-dependent and therefore exploitable statistically; this is the Minerva (TCHES 2020) /
TPM-Fail (CVE-2019-15809, CVE-2019-11090) / LadderLeak (CCS 2020) class, where a fraction of a
nonce bit per signature over many signatures recovers the key by lattice reduction.

**Severity: HIGH** (CLAUDE.md: "timing side-channel on secret data"). Present since signing
shipped at 3.5.9.

**Fix.** All of the above is replaced, for secrets, by the engine in §F2: `_ecs_sign_core` does
k·G, the affine conversion, k^-1 (Fermat, scalar-field Montgomery), r·d and e + r·d on it; the
RFC 6979 candidate test is `_ect_lt(k, n) & !_ect_is_zero(k)` with one branch on the verdict.
Signatures are byte-identical (RFC 6979 A.2.5 / A.2.6 KATs; the 82-assertion `ecdsa_sign.tcyr`,
`ecdsa_concurrent.tcyr` and the Authenticode ECDSA signer tests pass unchanged).

## F2 — The constant-time engine: structural review (no finding)

**Contract** (top of `src/ec_ct.cyr`): no `if` / loop condition on a secret, no secret-dependent
address, carries and borrows as top-bit arithmetic, the only multiply the 64×64 → 128 product.

**Function by function** (secret inputs → what they reach):

| Function | Secret inputs | Branches | Memory addresses |
|---|---|---|---|
| `_ect_add` / `_ect_sub` | operands | loops over nl (public) | fixed |
| `_ect_mul` (CIOS) | operands | loops over nl; final subtract by mask | fixed (`t[80]` stack) |
| `_ect_pow` / `_ect_inv` | base | loop over 64·nl; `if` on the bit of the **public** exponent p - 2 / n - 2 | fixed |
| `_ect_padd` / `_ect_pdbl` (RCB 2016 Alg. 4 / 6) | coordinates | **none** (straight-line) | fixed |
| `_ect_lookup` | the window digit | loops over 16 entries × limbs | every entry read; kept by mask |
| `_ect_smul` | scalar | loops over 16 (table) and nl·16 windows | digit extraction by public shift |
| `_ect_affine` | coordinates | none | fixed |
| `_ect_reduce_be` (keygen reduction) | random bytes | loops over bytes / bits / limbs | fixed |
| `_ect_reduce_once`, `_ect_cmov`, `_ect_lt`, `_ect_eq`, `_ect_is_zero` | operands | loops over nl; `r != a` pointer compare (public) | fixed |
| `_ecdh_keygen` | rnd, d | +1 carry loop over nl; `if (ok == 0)` (unreachable for valid curves) | fixed |
| `_ecdh_shared` | d | peer checks are on **public** data; one branch on the range-check **verdict** of d; one on the result being the identity | fixed |
| `_ecs_sign_core` | k, d | one branch on the public outcome r == 0 or s == 0 | fixed |

`CYRIUS_SYMS=<file>` (cycc 6.6.9) and each `_ect_*` / `_ecdh_*` / `_ecs_sign_core` function
disassembled; conditional branches counted (x86_64: `jcc`; aarch64: `b.cond` / `cbz` / `cbnz` /
`tbz` / `tbnz`, via llvm-objdump):

| Function | x86_64 | aarch64 | Source accounts for |
|---|---|---|---|
| `_nmul64_hi` / `_nmul64_hi_sw` | 0 / — | 0 / **0** (was 2) | — |
| `_ect_cmov`, `_ect_is_zero`, `_ect_eq`, `_ect_lt` | 1 each | 1 each | one limb loop |
| `_ect_load_be`, `_ect_store_be` | 2 | 2 | two nested loops |
| `_ect_add` / `_ect_sub` | 3 / 2 | 3 / 2 | limb loops |
| `_ect_mul` | 6 | 6 | zero-init, outer, two inner, final subtract, select |
| `_ect_pow` | 2 | 2 | exponent loop + public exponent bit |
| `_ect_padd` / `_ect_pdbl` | **0** / **0** | **0** / **0** | — |
| `_ect_lookup` / `_ect_smul` | 2 / 2 | 2 / 2 | entry + limb loops / table + window loops |
| `_ect_affine` | 0 | 0 | — |
| `_ect_reduce_be` / `_ect_reduce_once` | 4 / 2 | 4 / 2 | byte, bit, shift, subtract loops / limb loop + pointer compare |
| `_ecdh_keygen` / `_ecdh_shared` | 3 / 8 | 3 / 8 | carry loop + `ok` / five public peer checks + d verdict + identity verdict; +1 each for the compiler's `secret var` wipe loop |

| `_sigil_wipe64` | 1 | 1 | store loop |

No branch is unaccounted for. x86_64 lowers `MUL r64` (`_nmul64_hi`), data-independent on every
x86-64 sigil targets; aarch64 `MUL` is fixed-latency on the Cortex-A72 (pi) and Apple cores.

**Mathematical correctness.** The CIOS multiply, the a = -3 complete formulas and the fixed
window were checked against the existing (independent) verify-side arithmetic: 2000 random
field products / sums / differences per curve, 50 inversions, and k·G for small and random k on
both curves matched `fp_p256_*` / `pt_scalarmul` exactly during development; the suite then pins
the engine against external vectors (§F5).

## F3 — ECDH input validation (no finding)

- **Peer key.** Exactly `1 + 2·len` bytes; first byte `0x04`; X < p and Y < p compared as
  integers (never reduced — the x = p encoding of the valid point (0, y0) is refused by test,
  and, added after review, so is the y = 1 + p encoding of the valid point (x1, 1): that one
  satisfies the curve equation mod p, so it is the only vector that fails if the Y < p check
  alone is removed — the earlier y = p vector was off the curve as well);
  y² = x³ - 3x + b. This is SP 800-56A §5.6.2.3.3 full validation: both curves have cofactor 1,
  so an on-curve point other than the identity has order n, and the identity has no
  uncompressed encoding (the one-byte `0x00` SEC 1 form fails the length check). Compressed
  (`0x02` / `0x03`) and hybrid (`0x06` / `0x07`) forms are refused rather than decompressed.
  Validation runs on public data and may branch.
- **Private scalar.** 1 <= d <= n - 1, computed without a branch (`_ect_lt` & non-zero), then
  one branch on the verdict. d = 0, n, n + 1 and 2^bits - 1 are refused by test; d = 1, 2, n - 1
  give the expected x(Q), x(2Q), x(-Q).
- **Result.** d·Q at the identity is refused (unreachable after the checks above, kept fail-closed).
- **Every failure zeroes the output** (`secret_out`; both outputs for keygen), checked for every
  refusal in the suite with a 0xAA-prefilled buffer.
- **Aliasing.** Every input is read before an output is written, so `secret_out` may be `priv` or
  `peer_pub` and keygen's outputs may be `rnd`. **Found in review and fixed before release:** the
  first version zeroed `secret_out` before reading the peer key and the scalar, so a caller passing
  one buffer for both got -1 (the aliasing group: 8 assertions red on that draft, green now).
- **Keygen input.** Exactly len(n) + 64 bits are consumed (40 / 56 bytes; a longer buffer's tail
  is ignored, a shorter one is refused). d = (c mod (n - 1)) + 1 — FIPS 186-5 A.2.1 — lies in
  [1, n - 1] with a bias below 2^-64 and needs no retry. The entropy source is the caller's
  (cyrius's `random_bytes`); sigil does not draw it.

## F4 — Zeroisation: the signing nonce k survived the signer (MEDIUM, fixed)

*The first version of this section read "Zeroisation (no finding)" and said the signers' 8 KB
burn cleared "the dead frames below them". The review of the first 3.13.8 draft showed that was
false; this section is rewritten with what is true.*

**What was left.** After `ecdsa_p256_sign` returned, all eight 32-bit words of the RFC 6979 nonce
k lay in dead stack ~42.7 KB below the caller (the SHA-256 context layout, one word per 8-byte
slot), and words 0–3 again at 212–224 bytes. With k and the published (r, s),
d = r^-1(s·k − e): one signature plus one read of dead memory recovers the private key. 3.13.7
leaves the same class — the new test finds 17 words of k and d for P-256 and 30 for P-384 on the
3.13.7 sources — because HMAC has never wiped its context; what was new is that this audit's
first draft claimed it covered.

**Why.**
- `hmac_sha256` / `hmac_sha384` wiped K′, ipad and opad but not the SHA context or the inner
  hash (the comment called the inner hash "a public digest"). Under HMAC the context's final
  state IS the MAC; the HMAC_DRBG's last MAC is k, and in HKDF it is a derived key.
- `sha384_finalize` kept the whole SHA-512 output — under HMAC-SHA384, the MAC — in its scratch
  lane.
- The SHA-NI compress left the state in xmm1 / xmm2 / xmm7, a packed copy in its scratch and the
  last word in edx.
- The signers burned 8 KB, but their call tree reaches ~82 KB (P-256) / ~115 KB (P-384): the
  DRBG, HMAC and SHA scratch arrays are banked across 64 `cbank()` lanes, so their frames are
  large.
- The burn ran in the same function as the signer's `secret var` block, and that block's
  compiled epilogue saves rax / rdx / r8 / xmm0 / xmm1 below the frame after its wipe and never
  clears them (cyrius `EDEFER_SAVE`; [architecture note 005](../architecture/005-secret-var-epilogue-spills-registers.md)).
  xmm1 still held the SHA-NI state of the DRBG's last round: words 0–3 of k at 212 bytes.

**Severity: MEDIUM.** Recovering the key needs a second primitive that reads dead stack or
registers — an uninitialised-memory disclosure, a core dump, swap. Not exploitable alone, but it
turns any such read into key recovery from a single signature, and key zeroisation is a hard
rule here.

**Fix.**
- Both HMACs wipe their context and inner hash, and `sha384_finalize` its scratch after the copy,
  with `_sigil_wipe64` (8-byte stores; the exit wipes now cost less than the byte-loop memsets
  they replace — a short HMAC-SHA256 went from ~1.90 to ~1.67 µs).
- `_sha_ni_compress_one` clears xmm0–xmm7, its scratch state and edx at the end of the asm block;
  the AES-NI block functions clear xmm0 (a keystream block under GCM).
- Each signer is a plain wrapper around `_ecs_sign_p256` / `_ecs_sign_p384`, which hold the
  `secret var` block, and burns `_ECS_BURN_P256` / `_ECS_BURN_P384` = 128 / 160 KB after the
  callee — epilogue included — has returned. `_ect_burn_stack` covers any size (non-tail
  recursion over 16 KB frames) with 8-byte stores, so the larger burn costs no signing time.
  ECDH already burned from plain wrappers; its 8 KB is now the named `_ECDH_BURN` (its call tree
  is ~4.8 KB).
- A cleared local is not a wipe: zeroing SHA-256 finalize's `word` local did not remove the last
  digest word from that frame (a compiler temporary also held it), so per-call wipes of hash
  internals are not attempted; the signers' burn covers them.

**Evidence** (each red before the fix, on the tree or on a mutant):
- `ecdsa_sign.tcyr` "zeroisation": after each signer returns, a `secret var` function is called
  so that a register still holding a secret is spilled into the scanned region; then no 32-bit
  word of k or d, plain or byte-swapped, may appear at any byte offset of 192 KB of dead stack
  (first draft: 21 / 24 words; 3.13.7: 17 / 30; with only the SHA-NI clear removed: 4), and
  nothing the signer wrote may survive between the end of its burn and 192 KB (red with the
  burn at 64 KB / 96 KB: 33 / 80 words).
- `ecdsa_sign.tcyr` "HMAC": neither HMAC leaves its context state, SHA-384's finalize scratch or
  the inner hash in 96 KB of dead stack (red without the wipes: 3 / 4).
- `ecdh.tcyr` "zeroisation" now scans 64 KB rather than exactly the 8 KB the burn covers — a check
  sized by the thing it checks cannot see past it — calls the spill function, and checks that
  nothing the call wrote survives past the burn (red with a 1 KB burn: 117–138 words). Its
  private-key limb scan alone was not sensitive to the burn at all: d's limbs only ever sit in
  the `secret var` block, so none are found even with no burn; the intermediates the burn exists
  for are what the survives-past-the-burn check catches.
- Found and fixed earlier in this release (first draft): the burn wiped the LOW end of its pad
  (512 of 512 sentinel bytes survived), and a wipe issued from inside `_ecdh_keygen` could not
  reach that function's own spill slots (the d + 1 carry loop left the top limb behind).
- The RFC 6979 DRBG's banked V / K scratch is wiped per lane on every return, as before.

**Not covered** (residual, §F7): sigil's other `secret var` functions (Ed25519, X25519, HKDF, the
key parsers) are not restructured, so the cyrius epilogue spill applies to them until cyrius
clears the area (a draft issue went to the cyrius 6.6.15 integrator); HMAC / HKDF called outside
the signers wipe their own context and inner hash, but the SHA compression frames below them —
the software path's message schedule and working variables, a finalize temporary — are not wiped
per call; and `hmac_sha256` / `hmac_sha384` with a key longer than the block (64 / 128 bytes)
leaves the hashed key's SHA state in the one-shot `sha256()` / `sha384()` dead frame. Named for
the maintainer in the roadmap.

## F7 — Residuals (INFO)

- **Accept / reject branches.** The RFC 6979 loop branches on whether a candidate is in range;
  a rejected candidate is discarded, so the branch reveals only that one was rejected
  (probability ~2^-32 for P-256, ~2^-190 for P-384). ECDH branches on the validity verdict of d
  and on public peer-key checks. Inherent and harmless.
- **Software timing only.** The engine targets timing and cache channels. It does not randomize
  projective coordinates or blind the scalar, so it makes no claim against power or EM analysis
  of a single trace; the 3.13.1 point blinding was a timing fix for the old ladder and is not
  needed for that purpose any more.
- **Operand-value-dependent timing (the Hertzbleed class) is not addressed.** No branch and no
  address depends on a secret, but the time of a multiply chain can still depend on operand
  values through power and frequency. A dudect-style run on `ecdh_p256_shared` (9 000
  interleaved samples on one core, by the reviewer) separates d = 1 from random d at |t| = 5.6
  when only the fastest 20% of samples are kept (d = 1 about 2.3 µs, 0.09%, faster) and at
  |t| ≤ 1.3 uncropped; a fixed random-looking d against random d stays at |t| ≤ 2.4 at every
  crop, so the effect follows zero-valued operands, not a code path. Ephemeral ECDH scalars and
  RFC 6979 nonces are uniform, so practical exposure is low; closing it would need operand
  randomization (coordinate or scalar blinding).
- **Residue outside the secret-scalar entry points** — see F4 "Not covered". The cyrius fix
  (zero the defer walker's save area) closes the register half for every `secret var` function.
- **Codegen dependence.** The contract holds for the code cyrius 6.6.9 emits, checked above.
  A future compiler that turned a mask expression into a branch would break it; the
  disassembly check in architecture note 004 is how to re-verify after a toolchain bump.
- **aarch64 multiply.** The high half of each product is the software form on aarch64 (branch-free
  since this release). A native `UMULH` is a performance lever, not a correctness one (roadmap).
- **Verify stays variable-time** by design: every verify input is public.
- **Bench / perf.** Keygen and signing rebuild a 15-entry table of multiples of G per call; a
  precomputed constant-time comb would be ~4x faster (roadmap, maintainer's call).
