# Security Audit — 3.12.8 (2026-08-14)

**Scope.** This is a **scoped maintenance-cycle audit**, not a full P(-1)
sweep. The release changed no crypto path: it renames 14 error constructors,
bumps the toolchain pin 6.5.17 → 6.5.21, re-syncs `lib/`, and refreshes
`cyrius.lock`. The audit therefore covers (1) the rename's blast radius,
(2) what the new toolchain changed under sigil, and (3) a full-tree re-probe
of CLAUDE.md quirk #1, which is the invariant most likely to shift on a
compiler bump and the one that produced the 3.12.3 and 3.12.6 authentication
bypasses.

**Result: no findings. The audit floor stays empty.**

> ⚠️ **Process note.** Releases **3.12.3 through 3.12.7 filed no audit report
> at all** — a five-release lapse in the CLAUDE.md § "Security Hardening
> (before release)" step, which is unconditional. That stretch includes
> **3.12.6, which fixed an RSA-PSS authentication bypass**. This file
> re-establishes the practice for 3.12.8 only; it does **not** retroactively
> cover 3.12.3–3.12.7. Whether to run a catch-up audit over that range is not decided here.

## F1 — `err_*` → `sigil_err_*` rename: blast radius (INFO, no finding)

14 constructors in `src/sys_error.cyr` renamed; 124 call sites across 9 `src/`
files updated in the same mechanical pass.

Checked:

- **Name-only change.** Every rename preserves the body, arity, parameter
  order, packed/heap encoding and errno mapping verbatim. `git diff --stat`
  reports 124 insertions / 124 deletions — a 1:1 line correspondence with the
  call-site count, so no line was restructured under cover of the rename.
- **No collision with the existing `sigil_err*` surface.** `src/error.cyr`
  already defines `sigil_err`, `sigil_err_code`, `sigil_err_msg` and
  `sigil_err_free`. None of the 14 new names collides with those, nor with the
  `SIGIL_ERR_*` enum constants in `sys_error.cyr` (case differs and Cyrius is
  case-sensitive). Verified by grep before and after.
- **Completeness.** Zero bare `err_[a-z_]+` identifiers remain under `src/` or
  in any of the 14 `dist/` bundles. The single residual hit, `err_ptr` at
  `src/sys_error.cyr:12`, is prose inside a doc comment describing the `Err`
  payload — not an identifier.
- **No crypto exposure.** `sys_error.cyr` and its 9 callers
  (`certpin_core`, `dmverity`, `ima_core`, `luks`, `secureboot_core`,
  `sys_util`, `sysinfo`, `tpm_core`) are the trust-core syscall and plumbing
  layer. The rename touches no comparison, no key material, no zeroization
  site and no constant-time path. Constant-time posture is unchanged.
- **Failure direction.** These constructors only *build* `Err` values; none
  participates in an accept/reject decision. A hypothetical missed rename
  would be a **compile error** (undefined function), never a silent
  accept — the build is the oracle, and it is clean.

**Motivation, for the record.** The bare names were a live duplicate-symbol
collision, not a stylistic concern. kavach pins `[deps.sigil] tag = "3.12.7"`;
its vendored `lib/sigil.cyr` defines all 14 bare `err_*`, and its own
`src/sys_error.cyr` defines **the same 14 names** — 14 duplicate definitions in
a single link, resolved by include order rather than by intent. `agnodrm`,
`yukti`, `shabdakosh`, `agnostik`, `shabda` and `aegis` each carry their own
bare `err_*` and would collide identically on taking a sigil dep. A library
that publishes a bundle cannot own an unprefixed name.

## F2 — Quirk #1 re-probe under cycc 6.5.21 (INFO, no finding)

Quirk #1 is the invariant that broke twice in this minor: an array local past
the **122,880-byte per-fn stack budget** silently becomes a *shared global*,
and the compiler's `note: oversized array local kept in shared global (not
per-thread)` is the only reliable signal. Both prior bypasses came from
shared state on a verify path.

The smoke build under 6.5.21 emits **exactly two** such notes. Both were
attributed:

| Site | Size | Banked? |
|---|--:|---|
| `src/trust.cyr:501` — `hash_file_into`, `buf[262144]` | 262,144 B | ✅ `&buf + cbank()*4096` (4096 × 64 lanes) |
| `src/trust.cyr:502` — `hash_file_into`, `digest[2048]` | 2,048 B | ✅ `&digest + cbank()*32` (32 × 64 lanes) |

Both notes come from the **same function** — `hash_file_into`'s cumulative
array locals total 264,192 B, so the budget is blown by `buf` and `digest`
lands past it too. Both are already correctly banked across `cbank()` lanes,
and the banking is documented in-place. No action needed.

To rule out any *unbanked* over-budget function, a cumulative-budget scan was
run over every `fn` in `src/` (summing indented `var X[N]` array locals per
function, matching the compiler's cumulative accounting). **`hash_file_into` is
the only function in the tree that exceeds 122,880 B.** There is therefore no
unbanked shared-global array on any path, concurrent or otherwise.

The four other large arrays in `src/` — `_bn_mont_r2src[66560]`,
`_bn_exp_prod[65536]`, `_rsa_blind_prod[65536]` (and siblings) — are
**module-level globals by construction**, explicitly banked at
`N * SIGIL_CRYPTO_BANKS` with per-lane wipes on the secret paths (quirk #9 /
ADR 0004). They are not function locals and are not what the notes refer to.

**Not a regression:** the same two notes appear identically under the previous
6.5.17 pin. 6.5.21 changed nothing about this invariant.

## F3 — Toolchain and dependency integrity (INFO, no finding)

- `lib/` re-synced from the 6.5.21 snapshot; all **107** vendored `.cyr` files
  now match the snapshot **byte-for-byte** (verified by per-file `diff`). The
  prior shadow warning (`sigil 3.12.6 (pinned: 3.12.7)`) is gone.
- `cyrius.lock` hash-refreshed for the 10 libs that changed between the 6.5.17
  and 6.5.21 snapshots (`alloc`, `assert`, `atomic`, `bench`, `fdlopen`,
  `freelist`, `patra`, `sandhi`, `sigil`, `syscalls_windows`). Path set
  unchanged — a pure hash refresh, no dep added or dropped.
  `cyrius deps --verify`: **107 verified, 0 failed** (was 97/10).
- `cyrius vet` — 1 dep, **0 untrusted, 0 missing**. `cyrius deny` — **0
  violations**. `cyrlint` over all 9 changed files — **0 warnings, 0 untracked
  deferrals**.

> ⚠️ **Supply-chain observation (LOW, defence-in-depth, not fixed here).**
> With sakshi moved into `[deps].stdlib` at 3.12.7, sigil now has **zero git
> deps** — and `cmd_deps_lock()` (cyrius `cbt/deps.cyr:1916`) only writes the
> lock when `cyrius deps` actually *copied* something. So `cyrius deps` no
> longer refreshes `cyrius.lock` for this project at all. The lock was
> therefore stale-by-construction against `lib/` after the sync and had to be
> refreshed by hand. For a project whose whole job is trust verification, a
> tamper-detection record that silently stops tracking its own inputs is worth
> a permanent fix upstream. Not actioned in this release.
